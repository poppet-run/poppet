# Phase 31: Summaries of trimmed conversation history

[Implementation plan](../implementation-plan.md) · [Documentation index](../README.md)

Planned only. Extend the context assembly from phase 4 and the tool-free naming
request from phase 16 rather than adding a new memory system. Stored history stays
authoritative and unchanged. A summary is derived, replaceable data that the run
may read; it is never a source of facts, permissions, or saved memory.

### Goal and compatibility gate

`assembleContext` in `packages/agent/src/context.ts` keeps at most 20 complete
exchanges within the 256 KiB budget and silently drops older ones. Long CLI
sessions and Discord threads then lose earlier decisions unless the model
searches for them. Allow one bounded summary of the trimmed exchanges to join the
run's context, so the model knows what was discussed before the retained window
and where to look for detail.

First establish that the gap is real. The model can already call
`poppet_history.search_sessions` and `poppet_history.read_session` against the
current session. Record, for a set of long owner sessions, how many exchanges were
trimmed per run and whether answers missed earlier context that recall would have
found. Stop at this gate if recall closes the gap in practice; record the evidence
instead of building summaries. A better instruction to use recall on long
sessions is a smaller change and should be tried first.

Do not rewrite, delete, or merge saved messages, drop provider continuation from
retained exchanges, or change what `chat show`, search, or recall return. Do not
save facts from summaries, prompt the model to update memory before trimming, or
let a summary carry URL authorization, task changes, or command approval.

### Stage 31a: Observe trimming

Record on each run the number of eligible history exchanges and the number
selected into context, alongside existing usage. Show both in `chat show` run
inspection and, when `chat.logTimings` is enabled, in the worker log. This is
useful on its own and provides the measurement for the gate. It does not change
which exchanges are selected.

Add the counts to the run record in the store package's own migration. Existing
runs read as unknown, not zero. Keep the observation inside the run's existing
transaction; a failed or interrupted run records what it assembled before failing,
or nothing if assembly itself failed.

### Stage 31b: Generate and store a summary

Add a session summary record owned by `@poppet/store`: session ID, the last
message ID it covers, summary text of at most 8 KiB, the provider/model that
produced it, a summary prompt version, and the creation time. Keep one current
summary per session. Replacing it is a conditional write on the covered message
ID, so concurrent or late attempts cannot move coverage backwards.

`@poppet/agent` owns a tool-free summary request that follows the naming
request's pattern: the session's pinned selection, the existing model-access
permit, no tools, no continuation, no transcript writes, no automatic retries,
a 30-second deadline, and bounded output. Its input is the previous summary, if
any, plus the newly trimmed exchanges, limited to the material conversation
search already treats as eligible: user text and final answers from completed
runs. Tool arguments, tool results, page text, intermediate model text, profile,
skills, and saved facts are excluded. Cap the input at 64 KiB, taking the oldest
uncovered exchanges first, and leave the rest for a later attempt.

Request a summary only after a completed run whose next context would trim at
least four exchanges beyond the current summary's coverage. Run it after the
answer is printed or delivered and after session naming, so it never delays a
reply. A failed, cancelled, or malformed summary leaves the previous one in
place; the next eligible run tries again. Scheduled runs and occurrence sessions
do not generate summaries.

The summary instructions ask for decisions, open questions, and owner-stated
constraints, each with the session message IDs that support them, and forbid
instructions, permissions, or new claims. Retrieved and answered text is
untrusted historical data; injected text in old exchanges must not become an
instruction in the summary.

### Stage 31c: Use the summary in context

When a current summary exists and its coverage reaches the oldest selected
exchange, place it after the base instructions and saved facts in a block labelled
as a summary of earlier conversation, with the covered message range. Count it
against the context budget with its own 8 KiB cap. If coverage stops short of the
retained window, include the summary with a note that some exchanges are not
covered, rather than presenting it as complete. The newest input still has to fit
on its own; a summary never displaces the current exchange.

Add `chat.summaries` (default `false` during the trial) to enable generation and
use. `chat show` includes a `summary` object with its text, coverage, model, and
time, or `null`. `chat summary clear <session-id>` removes it; the next eligible
run may generate a new one. Clearing or disabling never affects stored history.

### Implementation reach and completion gates

| Area          | Required changes                                                                                         |
| ------------- | -------------------------------------------------------------------------------------------------------- |
| Agent         | Trimming counts from context assembly, summary request and instructions, summary placement and budgeting |
| Store         | Run trimming counts and session summary record in one migration, conditional summary replacement         |
| CLI           | `chat show` fields, `chat summary clear`, `chat.summaries` setting validation                            |
| Worker        | Post-delivery summary attempt for messaging sessions, ordered after naming under the existing permit     |
| Documentation | Chat context limits, configuration reference, storage schema, architecture context section               |

Test trimming counts with fixed histories, including failed runs, imported
exchanges, and the current exchange alone exceeding the budget. Test summary
generation with an injected model: threshold and coverage, the input cap leaving
remaining exchanges, exclusion of tool results and continuation, malformed and
timed-out responses keeping the previous summary, cancellation, and a late
attempt losing to a newer one. Test context assembly with summary, partial
coverage, no summary, and a summary that would not fit. Include an old exchange
containing instructions and check that the summary block stays labelled as data
and that no tool grant follows from it. Use temporary databases for migration
and verify existing runs and sessions are unchanged.

Run focused tests and `bun run check`. Manually hold one long CLI session and
one Discord thread past the trimming threshold with summaries enabled, and ask
about a decision from the trimmed part. Compare against the same question with
summaries disabled and recall available. Enable summaries by default only if
that comparison shows a clear improvement over recall alone. Fake-provider tests
do not establish summary quality or live provider behavior.
