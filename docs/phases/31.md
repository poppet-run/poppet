# Phase 31: Self-improvement from completed work

[Implementation plan](../implementation-plan.md) · [Documentation index](../README.md)

Planned only. Let Poppet learn reusable procedures and durable facts from its own
work without waiting for owner approval, following the learning loop of
[Hermes Agent](https://github.com/NousResearch/hermes-agent). Reuse the existing
skill loader, `Memory` service, tool journal, untrusted-content withdrawal, and
worker. Replace approval with automatic safeguards, visible change notices, and
revision history the owner can revert.

### Goal and safety model

Poppet should improve with use: choose relevant skills itself, record procedures
that worked, refine them when they fail, and keep facts it judges worth knowing.
The owner should notice each change and undo any of it, but never need to
approve one first.

This intentionally reverses several current rules: skills are owner-written and
explicitly selected, the model cannot write them, and memory changes need an
explicit current-user request. Each stage updates the affected guides when it
lands. Until then, [skills](../skills.md) and [memory](../memory.md) describe
current behavior.

Without approval, safety depends on these invariants:

- **Owner turns only.** Learning writes come from interactive turns that started
  with an owner message, or from background review of such a run. Scheduled runs
  never write skills or facts. `readOnlyTools` withdraws the new write tool.
- **Untrusted content stops writes.** The existing per-run withdrawal in
  `agent/conversation.ts` covers the new skill-write tool too. Once page, search,
  MCP, or attachment content enters a run, skill and memory writes stop until the
  next owner message. Review skips any run where withdrawal triggered, so fetched
  text cannot plant a lasting instruction.
- **Lasting changes stay narrow.** Learned skills and facts are instructions and
  context only. They cannot grant tool permissions, allowed URLs, MCP access, or
  task capabilities, or change `soul.md`, `profile.md`, configuration,
  credentials, or owner-written skill files.
- **Every change is attributed and reversible.** Each write records its prior
  content, source session, run, and call, and its origin (turn or review). Revert
  restores a previous revision as a new revision; history is never rewritten.
- **Every change is visible.** Replies list changes made in that turn. Later
  review changes appear on the next reply in that session and in the learning log.

Hermes's optional pending-write queue, skill hubs, downloads, supporting
reference files, scripts, and dialectic user modelling remain out of scope.

### Stage 31a: Model-selected skills, read-only

Implemented with automated checks; live model selection remains a manual check.

Build a skill index at run start from owner and (after 31b) learned skills. Each
entry has the name and a description: the first Markdown heading and the start
of the first paragraph, both bounded. Owner skills need no new format; optional
frontmatter is not parsed. The index is frozen for the run, counts toward
`POPPET_CONTEXT_BYTES`, and has its own budget (`POPPET_SKILL_INDEX_BYTES`,
default 8 KiB; `0` disables the index and tool). It considers at most 64 skills
and omits invalid files. If the index exceeds its budget, it lists names only,
then fewer names, and reports the truncation rather than failing the run.

Add the read-only `poppet_skills.view_skill` tool. It takes a name and returns
the validated name and content within `POPPET_TOOL_BYTES`; 31b adds the
revision. The result is
saved in the tool journal like any other tool result. Continuing the session
therefore uses the text the model actually saw, matching today's snapshot
guarantee without a session-level column. Instructions tell the model to check
the index before multi-step work and to view a matching skill before following it.

An explicitly selected `--skill` keeps its current snapshot behavior and stays
in the base instructions; the index marks it as already loaded. Scheduled runs,
messaging, and projects may use the index and view tool. Viewing grants nothing
beyond the run's existing permissions. Automatic session naming still receives
no skills.

### Stage 31b: Learned skills the agent writes

Implemented with automated checks; live checks of what a real model saves remain
manual. Writes are off unless `POPPET_LEARN_SKILLS` is set.

Store learned skills in SQLite rather than as files. This keeps each write, its
revision, and its journal receipt in one transaction, avoids races with external
editors, and leaves the owner's `skills/` directory untouched. Add a
`learned_skills` table (name, current revision, content, timestamps) and an
append-only `skill_revisions` table (name, revision, action, content or
tombstone, digest, source session/run/call, origin). Names follow the current
skill rules and are unique across owner and learned skills. An owner file always
wins: creating a learned name that matches an owner skill fails, and an owner
file added later shadows the learned skill, which the index then omits.

Add `poppet_skills.manage_skill` with the actions `create`, `patch`, `replace`, and
`delete`. Patching takes `old` and `new` strings and requires exactly one match.
`patch`, `replace`, and `delete` also require the revision returned by the run's
latest view or create of that skill. A stale revision fails and tells the model
to view the skill again, so concurrent turns and reviews cannot silently
overwrite each other. Results return the name, the new revision, and a short
acknowledgement, not the content.

Validation reuses the 8192-byte limit, UTF-8, and NUL rules. It also rejects
content that looks like credentials (private keys, bearer tokens, known API-key
shapes) and content above simple size or volume thresholds. Limits: at most 64
learned skills and 3 skill writes per run. The model can only patch or delete
learned skills. Editing owner files is deferred; to change an owner skill, the
model can create a learned variant under another name.

Instructions say when to save, as Hermes does: after a multi-step procedure
succeeded, after recovering from errors to a working path, or after the owner
corrected the approach. Skills should record a reusable procedure (inputs, steps
using existing tools, pitfalls, verification) and generalise private details.
They should capture lessons, not logs, and avoid repeating context already
supplied every run. Before creating a skill, the model should patch a similar
existing one.

Owner commands, with no model or credentials, through the worker when it is
running:

```sh
poppet skills list                     # owner and learned, with source and revision
poppet skills show <name>              # either kind
poppet skills history <name>
poppet skills revert <name> <revision>
poppet skills delete <name>            # learned skills only
poppet skills promote <name>           # create-only copy to skills/<name>/SKILL.md
```

Promoting copies the skill to the owner directory, after which the owner file
shadows the learned one. The draft-in-chat flow in the skills guide stays valid
as a manual alternative.

### Stage 31c: Agent-curated memory

Implemented with automated checks behind `POPPET_LEARN_MEMORY`; live checks of
what a real model saves remain manual. The review-origin restriction lands with
31d.

Allow the existing `poppet_memory.memory` tool to save, replace, and forget facts
the model judges durable and useful across sessions. Examples: stable
preferences, recurring project facts, and corrections the owner gave. It should
not save transient task state, secrets, content from untrusted sources, or facts
already in `profile.md`. The untrusted-content withdrawal and scheduled-run
exclusion stay unchanged.

Add an append-only `memory_revisions` table recording each fact's prior value,
action, origin (CLI, turn, or review), and source run/call. Facts gain an origin
column; existing rows migrate as CLI or turn based on `sourceRunId`. During
interactive turns the model may change any fact in its scope, as today, and the
reply notice shows the change. Background review may change only facts with
turn or review origin, never CLI-created facts.

When a write would exceed `POPPET_FACTS_BYTES` or the 128-fact limit, the tool
asks the model to consolidate or forget lower-value facts first instead of
failing silently. Keys and values keep their current schemas; project scoping is
unchanged. Add `poppet memory history [key]` and
`poppet memory revert <key> <revision>`, plus `--project` variants. Reverting a
forgotten fact recreates it.

### Stage 31d: Background review after qualifying runs

Implemented with automated checks behind `POPPET_LEARN_REVIEW`; live checks of
review quality remain manual.

After an interactive run completes, decide whether to review it. A run qualifies
when it used at least `POPPET_REVIEW_MIN_TOOL_CALLS` tool calls (default 5), or
when `POPPET_REVIEW_TURN_INTERVAL` completed runs (default 10) have passed in the
session since its last review. A qualifying run that read a page, search
results, an MCP result, or an attachment is recorded as skipped
(`untrusted-content`), and one that recalled history as skipped
(`history-recall`). Scheduled and attachment runs are never reviewed. Decisions go in
a `learning_reviews` table, unique per source run, with states pending, running,
completed, skipped, failed, or uncertain. Queueing is best-effort after the run
is saved and never fails the reply.

The worker drains pending reviews one at a time. Each review takes the same
agent permit as chats and tasks, so it never overlaps owner work, and polls
every 30 seconds when idle. A review is not a run: it adds no messages, run, or
journal entries to the session. Its writes are attributed to the reviewed run
with origin `review` and call IDs prefixed `review-<review id>-`. Without a
running worker, runs are only queued; the worker processes the queue when it
starts. Pending reviews older than `POPPET_REVIEW_MAX_AGE_HOURS` (default 24)
are skipped as `stale`, and reviews interrupted by a crash become `uncertain`
and are never replayed.

The review prompt includes the source run's owner messages, final answer, and
each tool call's name, status, and truncated arguments and output, within
`POPPET_REVIEW_INPUT_BYTES` (default 64 KiB); tool content shrinks before a
review is skipped as too large. It also includes the skill index and the
session's facts with their origins. It may use only `view_skill` and
`manage_skill` (when `POPPET_LEARN_SKILLS` is on) and the memory tool (when
`POPPET_LEARN_MEMORY` is on), with the same validation, at most 3 skill and 5
fact changes, and at most 4 model turns. It cannot change facts with CLI
origin. Its final text is stored as the review summary. It uses the session's
provider and model; a separate review model is deferred. Failures mark the
review failed, or uncertain when a write may have committed.

### Change notices

Reviews that changed something produce a notice on the next CLI chat run in
that session, printed with the session and run lines, for example
`Since last time: learned skill weekly-review (r1); saved fact answer.style.`
Each notice is shown once. Messaging replies are built from the saved run
result, so they do not show notices yet; those reviews remain listed by:

```sh
poppet learning reviews [--state s] [--limit n]
```

Changes made during a turn are reported by the model in its reply, as
instructed; host-generated per-turn notices, a combined `learning log`, and a
notices setting are deferred. `skills history` and `memory history` provide the
full record.

### Configuration

| Key                            | Default | Purpose                                   |
| ------------------------------ | ------- | ----------------------------------------- |
| `POPPET_SKILL_INDEX_BYTES`     | `8192`  | Skill index budget; `0` disables it (31a) |
| `POPPET_LEARN_SKILLS`          | `false` | Learned-skill writes (31b)                |
| `POPPET_LEARN_MEMORY`          | `false` | Agent-curated facts (31c)                 |
| `POPPET_LEARN_REVIEW`          | `false` | Background review (31d)                   |
| `POPPET_REVIEW_MIN_TOOL_CALLS` | `5`     | Tool-call threshold for review            |
| `POPPET_REVIEW_TURN_INTERVAL`  | `10`    | Completed runs between session reviews    |
| `POPPET_REVIEW_INPUT_BYTES`    | `65536` | Review transcript budget                  |
| `POPPET_REVIEW_MAX_AGE_HOURS`  | `24`    | Skip stale reviews                        |

Each setting also has a `chat.*` key in the configuration file. Write features
default off until their live checks pass, then default on in a later release.

### Implementation reach and completion gates

| Area          | Required changes                                                                                                                                                       |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Store         | Migrations for `learned_skills`, `skill_revisions`, fact origin, `memory_revisions`, `learning_reviews`, an internal review run kind, and notice delivery state        |
| Agent         | `skills.ts` index and view, `poppet_skills.manage_skill`, withdrawal and `readOnlyTools` coverage, instruction changes, memory-tool policy, review prompt and tool set |
| Memory        | Origin and revisions in `LocalMemoryLive`, review-origin restriction, history and revert operations                                                                    |
| Worker        | Review queue draining, priority below owner runs, stale skipping, restart and recovery                                                                                 |
| CLI, gateway  | `skills history/revert/delete/promote`, `memory history/revert`, `learning log/reviews`, notices in replies and `/status`, worker command schemas                      |
| Documentation | Skills, memory, chat, configuration, storage, architecture, worker, CLI; replace "explicit only" wording as each stage lands                                           |

Test that scheduled runs and runs with withdrawn tools cannot write skills or
facts, including fabricated calls. Test that review skips untrusted and recall
runs, and that stale revisions fail. Cover these: owner skills shadow learned
ones, revert creates a new revision, and review cannot change CLI facts.
Exercise byte, count, and per-run limits, secret-shaped rejection, index
truncation, and journal-backed continuation after a learned skill changes. Also
cover duplicate review enqueueing, crash during a review write (uncertain, no
replay), and migration from existing facts. Use injected providers that make
scripted learning calls.

Run focused tests and `bun run check` per stage. Live checks: complete a real
multi-step procedure, confirm the model saves a sensible skill, start a fresh
chat and confirm the model selects and follows it. Then correct its approach and
confirm a patch, and revert it from the CLI. For memory, state a preference
indirectly and confirm the fact and notice. For review, confirm a qualifying
run produces a later "since last time" notice and an unqualified one does not.
Fake-provider tests cannot establish that a real model learns useful, general
procedures rather than noise; record observed quality and adjust instructions
and thresholds before enabling writes by default.
