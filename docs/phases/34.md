# Phase 34: Model and reasoning selection for new sessions

[Implementation plan](../implementation-plan.md) · [Documentation index](../README.md)

Planned only. Let the owner choose a provider, model, and reasoning effort when a
session or task is created, from the CLI and from Discord `/new`. Sessions
already pin their provider, model, and workload; this phase adds a choice at
creation and one new pinned setting. Changing the selection of an existing
session is outside this phase because provider continuation belongs to one
provider and model.

### Goal and compatibility gate

`chat new`, `chat interactive`, `tasks add`, and Discord `/new` all use the
configured `provider` and `model`. Trying another model means editing
`config.json`, and `ModelRequest.settings` has no reasoning control, so every
request uses each provider's default effort. Allow an explicit selection at
creation, keep the configured default when none is given, and never fall back to
another model when the selected one is unavailable.

First verify each adapter's actual controls. For ChatGPT, OpenRouter, and
OpenCode Go, record whether the pinned API accepts a reasoning effort, the
accepted values, how the model listing reports support, and the failure when an
unsupported value is sent. Check whether resolving a `ModelDescription` needs a
network call, its deadline, and whether a cached listing exists. Stop at this
gate for effort if no adapter can report support from model metadata; model
choice can still proceed alone.

### Stage 34a: Reasoning effort as a provider capability

Add `reasoningEffort` to `GenerationSetting` and an optional
`settings.reasoningEffort` to `ModelRequest`, using a provider-neutral set such
as `low`, `medium`, and `high`. Each adapter maps the values it supports and
advertises the capability only for models whose metadata confirms it. A model
without the capability rejects an explicit effort at selection time, never at
inference time. Unset means the provider default, which is current behavior.

Pin the effort on the session and task beside provider, model, and workload, in
the store and tasks packages' own migrations. Existing sessions and tasks read as
unset. Main conversation turns use the pinned effort. Session naming and
command review keep the provider default so their existing deadlines hold; state
this in the architecture section rather than letting each caller decide.

### Stage 34b: Selection at creation

Add `--provider`, `--model`, and `--effort` to `chat new`, `chat interactive`
when it creates a session, and `tasks add`, placed before the message like the
existing options. Resolve the model description before creating the session or
task, check credentials with the existing status reader, and reject unknown
models, missing credentials, unsupported effort, and incompatible workloads
before anything is saved. The OpenCode Go `coding` workload rule stays enforced
by its adapter.

Add optional `models` aliases to configuration, each naming a provider, model,
and optional effort, for example `fast` or `deep`. The CLI accepts an alias or
an explicit provider and model. Discord `/new --model <alias> [--effort <value>]`
accepts aliases only, so a chat message cannot select an arbitrary paid model
and the owner does not type long model IDs. An alias effort can be overridden
only with a value the model supports.

Tasks created through `poppet_tasks.manage_tasks` keep inheriting the current
session's selection, now including effort. Model arguments cannot select a
provider, model, alias, or effort. `tasks edit` does not change the selection in
this phase; create a replacement task instead.

### Stage 34c: Inspection

`chat show`, `chat sessions`, `tasks show`, and Discord `/status` report provider,
model, effort, and alias name when one was used. Saved runs keep recording the
selection they used. `poppet config` lists aliases without secrets. The
interactive prompt shows the selection when the session opens.

### Implementation reach and completion gates

| Area          | Required changes                                                                                    |
| ------------- | --------------------------------------------------------------------------------------------------- |
| Provider      | `reasoningEffort` setting and capability, per-adapter mapping and metadata, contract test cases     |
| Store, tasks  | Pinned effort on sessions and tasks in each package's migration, read as unset for existing records |
| Agent         | Pinned effort on main turns only, unchanged settings for naming and review                          |
| CLI           | Selection options, pre-save validation, alias resolution, inspection fields                         |
| Gateway       | `/new --model` and `--effort` parsing, alias-only selection, `/status` fields                       |
| Config        | `models` alias schema and validation at startup                                                     |
| Documentation | CLI, chat, tasks, Discord, configuration, provider guides, architecture provider interface          |

Extend the shared provider contract cases with effort set, unset, and rejected
for an unsupported model. Test selection validation with injected resolvers:
unknown provider, unknown model, missing credentials, unsupported effort, coding
workload mismatch, and alias override. Verify nothing is saved when validation
fails, existing sessions and tasks behave as before, chat-created tasks inherit
effort, and Discord rejects explicit model IDs. Use temporary databases for both
migrations.

Run focused tests and `bun run check`. Manually start one CLI session and one
Discord thread with an alias and a non-default effort, and confirm the request
settings in the provider's own logs or response metadata where available, and
the selection in `chat show` and `/status`. Fake-provider tests do not establish
that a live provider applied the requested effort.
