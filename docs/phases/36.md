# Phase 36: MCP server setup and OAuth sign-in

[Implementation plan](../implementation-plan.md) · [Documentation index](../README.md)

Implemented on the `mcp-oauth` branch; the live OAuth check below has not run.
Let the owner add and remove remote MCP servers from the CLI, and
sign in to Streamable HTTP servers that require OAuth. Today servers are added
by editing `config.json`, bearer tokens must be provisioned as protected
credential files by hand, and OAuth servers need a stdio bridge that owns the
sign-in.

### Goal and compatibility gate

Sign-in is an owner action in the CLI. The worker, messaging, and scheduled runs
use and renew saved tokens without interaction. A run never starts an
authorization flow: a missing token, a rejected refresh, or a step-up request
makes that server unavailable with a diagnostic naming `poppet mcp login <id>`,
and built-in tools remain available.

The pinned client SDK (2.3.1) implements protected resource metadata
discovery (RFC 9728), authorization server metadata (RFC 8414 and OpenID
discovery), dynamic client registration, PKCE, resource indicators, refresh,
and step-up through `OAuthClientProvider` and `auth()`. Use it rather than a
second implementation. First verify, against a fixture authorization server
under Bun 1.4.4, that:

- `ScopedHTTPTransport` accepts an `authProvider` while keeping `boundedFetch`,
  the same-origin endpoint redirect policy, and the 8-second startup deadline.
- Authorization-server metadata and token responses can pass through the same
  size cap.
- A metadata `issuer` that does not match its discovery URL is rejected, and
  tokens are bound to the configured resource.

Stop at this gate if any check fails, and decide whether to wrap or replace that
part of the SDK before continuing.

### Stage 36a: Server management commands

Add `poppet mcp add <id> --url <url> --auth <none|api-key|oauth>` with
repeatable `--tool <name>` and `--scheduled-tool <name>`, and
`poppet mcp remove <id>`. `--auth` is required; nothing infers the scheme from
a server response.

- `api-key` reads the key from a hidden prompt or `--key-stdin`, never an
  argument. It saves the protected credential `mcp-<id>` and writes the header
  `Authorization: { "credential": "mcp-<id>", "prefix": "Bearer " }`.
  `--header <name>` and `--prefix <text>` cover schemes such as `X-API-Key`.
- The command builds the new `mcpServers` array and validates it with the
  existing schema before writing through `updateConfigFile`, so unique IDs, the
  server limit, header rules, and the scheduled subset are enforced in one
  place and other configuration keys are preserved.
- After saving, it connects once and prints the discovered tool names. Without
  `--tool`, the allowlist is empty; the owner reviews the names and adds
  allowed tools explicitly. Discovery failure does not undo the saved entry.
- A `none` or `api-key` server answering 401 with protected resource metadata
  fails with a diagnostic suggesting `--auth oauth`.
- `remove` deletes the entry and its credential or token file.
- Both commands remind the owner that the worker reads settings at start and
  must be restarted.

Stdio servers stay hand-configured. These commands are CLI-only; chat and
messaging cannot add, remove, or sign in to servers. This stage has no OAuth
dependency and can ship alone.

### Stage 36b: Shared browser sign-in

Move the browser launcher, loopback callback listener, pasted-callback
fallback, and confirmation page from `packages/provider-openai/src/sign-in/`
into a new small workspace package. The shared callback owns `state`, PKCE,
the callback path, and origin checks. ChatGPT's `nonce`, issued `clientId`, and
identity checks stay in the OpenAI provider. ChatGPT sign-in tests pass
unchanged, and `--no-browser` and `--callback-port` behave the same for both.

### Stage 36c: OAuth configuration and token storage

HTTP entries accept an optional `oauth` object, written by
`mcp add --auth oauth [--client-id <id>] [--scope <scope>]… [--callback-port <port>]`:

```json
{
  "oauth": {
    "clientId": "optional pre-registered client",
    "clientSecret": { "credential": "optional-secret" },
    "scopes": ["optional", "scopes"],
    "callbackPort": 1455
  }
}
```

An entry cannot combine `oauth` with an `Authorization` header, and stdio
entries cannot use it. Add a versioned JSON record store to
`@poppet/credentials` beside `ApiKeyStore`, with the same `0700` directory,
`0600` regular file, owner lock, and symlink, hard-link, and FIFO rejection.
`<data directory>/auth/mcp-<id>.json` holds the issuer, client registration and
its redirect URI, tokens with expiry and granted scopes, cached discovery state,
and the server URL and resource it was issued for. A changed URL or resource
makes saved tokens unusable until the owner signs in again. The PKCE verifier
and `state` exist only in memory during sign-in.

### Stage 36d: Sign-in commands

`mcp add --auth oauth` signs in after saving unless `--no-login` is given.
`poppet mcp login <id>` signs in again and `poppet mcp logout <id>` clears
tokens while keeping the registration. Client registration uses a configured
`clientId`, otherwise dynamic registration when the authorization server offers
it, otherwise fails with a diagnostic asking for a pre-registered client.
Client metadata documents are unsupported because Poppet has no public HTTPS
address to host one. A redirect URI with a different port triggers a new
registration. A server waiting for sign-in rechecks its saved record on every
request without contacting the server, so a running worker reconnects on the
first request after `mcp login` and needs no socket command.

### Stage 36e: Runtime tokens and refresh

The HTTP transport receives an auth provider backed by the record store:

- Refresh holds the record's lock and rereads it first, so the worker and a CLI
  process never both spend a rotating refresh token.
- An `invalid_grant` refresh clears tokens and reports a new `needs-login`
  state, which does not retry until the next login. Network and server failures
  keep tokens and use the existing backoff.
- `redirectToAuthorization` fails immediately outside `mcp login`, including
  for 401 and `insufficient_scope` step-up responses.
- The transport's single retry after a 401 is safe because the server rejected
  the request before processing it.
- The current access token joins the redaction set for each call, since
  refresh changes it.
- `mcp servers` reports the auth scheme, sign-in state, token expiry, and
  granted scopes, never token values.

### Out of scope

Unattended grants (`client_credentials`, private-key JWT; the SDK's
`ClientCredentialsProvider` makes this a small follow-up), client metadata
documents, device authorization, OAuth for stdio servers, the legacy HTTP+SSE
transport, interactive tool selection during `mcp add`, and adding stdio
servers from the CLI.

Extend the in-process HTTP fixtures with a fake authorization server providing
protected resource metadata, authorization server metadata, dynamic
registration, and a token endpoint that rotates refresh tokens. Test:

- `mcp add` with each scheme writes valid configuration, rejects duplicates and
  the ninth server without writing, and never accepts a key as an argument.
- Login then a tool round trip; an expired access token refreshes silently.
- A rejected refresh reaches `needs-login` without opening a browser, and a run
  or step-up response never starts authorization.
- Two processes refreshing at once leave one valid token set.
- A changed URL makes saved tokens unusable.
- A server echoing the access token has it redacted.
- `remove` and `logout` delete the right files only.

Run focused tests and `bun run check`. Manually, with one real server that
supports dynamic registration: add it with `--auth oauth` and sign in over SSH
with a pasted callback, complete a CLI and a worker tool round trip, force a
refresh, log out, and confirm `mcp servers` shows `needs-login`. Add one
bearer-token server with `--auth api-key --key-stdin` and complete a round trip.
Fixture tests do not establish that a real authorization server interoperates.

### Implementation record

The gate passed on 2026-10-29 against the fixture authorization server under
Bun 1.4.4: discovery, dynamic registration, the PKCE code exchange, 401-driven
refresh through `boundedFetch`, rejection of a mismatched metadata issuer, and
token clearing on `invalid_grant`. The SDK sends a transport's `requestInit`
headers to authorization servers when it drives a 401 itself, so OAuth servers
use Poppet's own auth provider and OAuth fetch instead; configured headers reach
only the MCP endpoint. A running server that answers 403 `insufficient_scope`
fails that call as a permission error naming the scope rather than an uncertain
call.
