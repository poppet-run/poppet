# Phase 36: Multiple instances of one messaging adapter

[Implementation plan](../implementation-plan.md) · [Documentation index](../README.md)

Planned only. Let one worker run several configured instances of the same
messaging adapter, such as two Discord servers or a personal and a work Slack
workspace. Discord and Slack already run side by side, each with its own fresh
`GatewayLive`; this phase removes the assumption that an adapter type names
exactly one gateway. Running several workers against one data directory stays
outside this phase because the store lock allows one owner process.

### Goal and compatibility gate

Today the adapter ID is the identity of a gateway everywhere. `config.json` has
one `discord` and one `slack` section, credentials live in one
`channels/<adapter>.json`, `validateChannels` rejects a second registration with
the same ID, and `ChannelRegistration.load` takes no instance argument. Task
destinations and `MessagingWorker.resolveDestination` select by adapter, so two
Discord instances cannot be told apart.

Scheduled delivery would also misbehave. In `packages/gateway/src/repository.ts`,
`scheduled` and `failedScheduled` filter on `destination.adapter` only, so each
instance would claim the other's occurrences, and `rejectScheduledDeliveries`
fails pending deliveries whose account differs from the current one, so each
instance would fail the other's deliveries at startup.

First verify that two instances of one type can coexist in the SDKs. Start two
Discord clients with different bot tokens in one Bun process and two Slack
Socket Mode connections for different workspaces, and confirm neither shares
global state such as a default client, rate-limit bucket, or process-wide
listener. Stop at this gate for an adapter whose SDK cannot run two independent
connections; the other adapter can still proceed.

### Stage 36a: Instance names as the routing key

Give each channel an instance name, separate from its adapter type, using the
existing ID pattern `^[a-z][a-z0-9-]{0,63}$`. The instance name is the value
stored in the gateway tables' `adapter` columns and in
`DeliveryDestination.adapter`; the channel carries its type as a separate field
for setup, help, and status. The default instance of each type is named after
the type, so existing bindings, inbox rows, tasks, and `--to discord:<id>` keep
their meaning and no migration is needed.

Once every instance has a distinct name, the scheduled delivery queries are
scoped correctly without changing their SQL. Add a repository test with two
instances of one type that each claim only their own occurrences and failure
notices and leave the other's pending deliveries untouched.

### Stage 36b: Configuration and registration

Keep the top-level `discord` and `slack` sections as the default instances. Add
an optional `gateways` map for additional instances, keyed by instance name:

```json
{
  "gateways": {
    "discord-work": {
      "type": "discord",
      "ownerId": "200",
      "guildId": "300",
      "homeChannelId": "400"
    }
  }
}
```

Each entry is validated with its type's existing policy schema. Credentials are
saved in `channels/<instance>.json`; `loadChannelSettings` already keys files by
name. Reject at startup an instance name that equals a registered type other
than its own, a duplicate name across the two forms, and an unknown type. A
malformed entry disables only that instance and reports the error, as a
malformed `discord` section does today.

Add `instance` to `ChannelEnvironment` so a registration's `load` and `setup`
know which instance they serve, and make `configuredChannelSettings` take the
instance name instead of the hard-coded `"discord" | "slack"` key. External
packages receive the same field; one that ignores it still loads its default
instance. `MessagingWorkerLive` builds one fresh `GatewayLive` per configured
instance rather than per registration, and supervises each separately.

### Stage 36c: Setup and task destinations

`poppet gateway <type> setup --name <instance> ...` configures an additional
instance and writes its `gateways` entry and credentials; without `--name`,
setup configures the default instance as now. `poppet setup` keeps offering the
default instances only. Removing an instance stays manual in this phase: delete
its config entry to disable it, as for the top-level sections, and the saved
credentials remain.

`tasks add --to <instance>:<conversation-id>` selects an instance;
`tasks list`, `tasks show`, and the chat task tool report the instance name. In
messaging, `here` and `home` resolve against the instance the current message
arrived on, and the existing rule that explicit destinations must belong to the
current gateway means the current instance. Model arguments still cannot select
another instance.

### Stage 36d: Isolation checks and inspection

Each instance has its own owner, scope, home channel, inbox cap, and supervision.
When two instances authenticate as the same bot account, disable the later one
with a status error, because they would otherwise share deduplication and the
64-entry pending cap. Memory and recall remain shared across instances under the
single-owner policy; state this in the architecture section.

`worker status` adds `type` and `instance` to each `channels` entry, and logs
annotate the instance. The doctor messaging hint names the failing instance.
All instances keep the worker's configured provider and model; per-instance
model selection is outside this phase and would build on
[phase 34](34.md) aliases.

### Implementation reach and completion gates

| Area          | Required changes                                                                                     |
| ------------- | ---------------------------------------------------------------------------------------------------- |
| Config        | `gateways` map schema, name and type validation, default-instance mapping of `discord` and `slack`   |
| Gateway       | Instance name on the channel, `ChannelEnvironment.instance`, instance-keyed settings and credentials |
| Channels      | Discord and Slack registrations load and set up a named instance                                     |
| CLI           | Per-instance worker composition, `setup --name`, instance destinations, status fields                |
| Tasks         | Instance names in destination parsing and output; no schema change                                   |
| Documentation | Configuration, Discord and Slack guides, adding a channel, architecture messaging gateway, worker    |

Test with injected channels: two instances of one type accept, bind, and deliver
independently; scheduled results and failure notices reach only their own
instance; a duplicate bot account disables the later instance; malformed and
conflicting `gateways` entries disable only themselves; existing default-instance
records and tasks behave as before. Use temporary databases for the repository
cases.

Run focused tests and `bun run check`. Manually connect two Discord servers with
different bots, or two Slack workspaces, through one worker; confirm each thread
replies on its own instance, a scheduled task with `--to <instance>:<id>` posts
only there, and `worker status` lists both instances. Injected-channel tests do
not establish that the SDKs run two live connections independently.
