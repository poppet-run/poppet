# Phase 33: Trusted time for scheduled runs

[Implementation plan](../implementation-plan.md) · [Documentation index](../README.md)

Planned only. Supply each scheduled occurrence with host-derived time facts in its
run instructions. This closes the follow-up requirement recorded by phase 30's
recurring trials. Do not add prompt templates, date placeholders, or a scheduling
language; the saved prompt stays plain text.

### Goal and compatibility gate

`packages/agent/src/conversation.ts` adds the current UTC time only when the
interactive task tool is available. `executeOccurrence` in
`packages/tasks/src/scheduler.ts` sends the saved prompt with read-only tools and
no time at all, so a recurring "summarize today's agenda" depends on the model's
guess. Give the run the occurrence's scheduled time, its actual start time, and
the task's timezone, so the model can resolve "today", "this week", or "since the
last run" from trusted values.

First confirm what each occurrence kind records. Check `scheduledAt` for an
on-time cron occurrence, a catch-up run after sleep, a snoozed execution, a
one-off, `run_now`, and `retry`, and whether the previous successful occurrence's
scheduled time is available cheaply. Confirm where instruction text reaches each
provider adapter and that it is excluded from saved history. Stop and record the
gap if any kind lacks a meaningful scheduled time; do not invent one from the
start time.

### Stage 33a: Time facts in occurrence instructions

Pass an occurrence time context from the scheduler through `agent.send` options:
scheduled time, start time, the task's IANA timezone (UTC for one-off tasks), the
occurrence kind, and the previous successful occurrence's scheduled time when one
exists. The conversation builder renders these as a short instruction block, in
UTC and in the task's local time with its offset, derived from stored UTC
milliseconds so DST gaps and repeats render unambiguously.

The block states that reporting windows are anchored to the scheduled time, not
the start time. A catch-up or retried occurrence therefore reports the window it
was scheduled for, and also knows how late it is running. `run_now` occurrences
are anchored to the time they were queued and say so. The model receives no
instruction to change task schedules or create follow-up tasks from these facts.

Time facts are host data, not owner instructions. They cannot authorize tools,
URLs, memory, or task changes, and a skill or saved prompt cannot override them.
Keep the existing interactive task-tool time line unchanged in this phase.

### Stage 33b: Inspection and reproducibility

The instruction block is not saved as a message. Make sure `tasks show` reports
each occurrence's scheduled time, start time, kind, and the timezone used, so an
owner can reconstruct what the run was told. Add a stored field only if the gate
shows one is missing; prefer deriving from existing occurrence and run records.

Document the behavior in the scheduled tasks guide, with an example prompt such as
"Summarize my calendar for the scheduled day" and the note that windows follow
the scheduled time. Update phase 30's recurring trials to depend on this phase
instead of stopping at the time-source gate.

### Implementation reach and completion gates

| Store         | None expected; a field only if the gate finds an occurrence kind without a usable scheduled time   |

Test with a controllable clock: an on-time cron occurrence, a catch-up after a
missed window, a snoozed execution, a retry hours later, `run_now`, a one-off,
and occurrences across spring and autumn DST in `Europe/London` and a timezone
with a non-hour offset. Assert the rendered instruction values against the stored
records rather than the wall clock, and that interactive chat instructions are
unchanged. Check that the block never enters saved history.

Run focused tests and `bun run check`. Manually schedule a one-minute recurring
task that asks for the scheduled local date and time, let one occurrence run on
time and one after a worker restart past its due time, and compare both answers
with `tasks show`. A correct date in the answer shows the model received the
facts; it does not establish that a model applies reporting windows correctly
for every prompt.
