# Phase 32: Host commands in an isolated container

[Implementation plan](../implementation-plan.md) · [Documentation index](../README.md)

Planned only. Add an optional container backend for `poppet_system.bash` behind
the existing tool contract. Keep the host backend as the default and keep model
review, Discord approval, and scheduled failure behavior unchanged. The container
reduces what an allowed command can reach; it does not replace review.

### Goal and compatibility gate

Today `apps/cli/src/bash.ts` runs `/bin/bash` as the owner's account with
Poppet's environment, and the only barrier is an LLM review that the
[host commands guide](../commands.md) already calls fallible. Allow the owner to
run commands instead in a container that sees only explicitly listed
directories, receives no host environment or credentials, and has no network
unless configured. Scheduled runs, which cannot obtain approval, benefit most.

First choose one runtime and verify it through its CLI on macOS and Linux.
Candidates are Docker-compatible CLIs (Docker Engine, Docker Desktop, OrbStack,
Colima, Podman) and Apple's `container` on macOS. For the chosen runtime, verify
with a disposable image: no network, read-only and read-write bind mounts at the
same absolute paths, a non-root user, memory/CPU/process limits, stdin closed,
bounded startup time, killing and removing the container on timeout and
cancellation, and finding leftover containers after a worker crash by label.
Record measured startup and per-command latency.

Stop at this gate if the runtime cannot enforce mounts, network, and cleanup
from Poppet's own process, or if it requires mounting its control socket into
the container. Never expose a runtime socket, the Poppet data directory, or the
credentials directory to commands. Do not fall back to the host backend when
the container backend is configured but unavailable.

### Stage 32a: Configuration and lifecycle

Add a `commands` setting:

| Field               | Default | Purpose                                                                  |
| ------------------- | ------- | ------------------------------------------------------------------------ |
| `backend`           | `host`  | `host` or `container` for interactive runs                               |
| `scheduledBackend`  | `host`  | `host` or `container` for scheduled runs; can be stricter than `backend` |
| `container.image`   | Unset   | Image reference pinned by digest; required for the container backend     |
| `container.mounts`  | `[]`    | Absolute host directories, each `read-only` or `read-write`              |
| `container.network` | `none`  | `none` or the runtime's default network                                  |
| `container.env`     | `[]`    | Environment variable names copied from Poppet's process                  |
| `container.limits`  | Bounded | Memory, CPU, and process limits with conservative defaults               |

Validate configuration at startup: mounts must be existing absolute directories,
must not overlap the data directory or credentials, and must not be `/` or the
home directory itself. Environment names are copied only if listed; nothing else
from the host environment enters the container. Poppet never pulls images during
a run. A missing image is a clear configuration error with the pull command to
run.

Start one container per run on the first Bash call and remove it when the run
ends, mirroring the browser's per-run lifecycle in phase 21. Each invocation is
an exec into that container with its own deadline. Label containers with the run
ID; a new worker owner removes labelled containers left by an interrupted run
before accepting work. Commands share filesystem state only within one run and
through read-write mounts.

### Stage 32b: Tool, review, and execution contract

The tool's description and the review request both state the backend, mounts
and their modes, and network setting, so the model plans for the environment and
the reviewer judges the actual effect. The review policy and its decisions are
unchanged in this phase. Relaxing approval thresholds for sandboxed commands is
a separate owner decision after evidence, not part of this plan.

Reject a working directory outside the configured mounts before review, saving a
model request, with a result that names the allowed directories. Output bounds,
exit codes, truncation, and the uncertain outcome of interrupted or timed-out
commands keep their current meaning. Timeout and cancellation kill the exec and,
if it does not stop promptly, the whole container; a killed container fails the
remaining commands in that run rather than being silently restarted.

The tool journal records the backend and container identity for each invocation,
and `chat show` and `tasks show` include them. Discord approval prompts show the
backend so the owner knows whether an approved command runs on the host.

### Implementation reach and completion gates

| Area          | Required changes                                                                                   |
| ------------- | -------------------------------------------------------------------------------------------------- |
| Config        | `commands` schema, validation of mounts, image, environment names, and limits                      |
| CLI           | A container runner beside the host runner behind the existing `Bash` service, per-run lifecycle    |
| Agent         | Backend facts in the tool description and review input, working-directory check before review      |
| Worker        | Leftover container cleanup on owner start, backend selection for scheduled runs                    |
| Store         | Backend and container identity in the tool journal, if not representable in existing records       |
| Documentation | Host commands guide, configuration reference, runtime setup, security limits of the chosen runtime |

Test with the chosen runtime behind an injected runner interface for unit cases,
and against the real runtime in a separately marked integration suite: allowed
and refused working directories, read-only mount writes failing, no network,
no host environment leakage, limits enforced, timeout and cancellation removing
the container, crash cleanup by label, missing image, unavailable runtime with no
host fallback, and scheduled runs using `scheduledBackend`. Keep existing host
backend tests unchanged.

Run focused tests, the integration suite where the runtime is installed, and
`bun run check`. Manually run one interactive command and one scheduled task
with the container backend, confirm a write outside the mounts fails, and
confirm no labelled containers remain afterwards. A passing suite shows the
configured boundaries hold for the tested runtime version; it does not make the
runtime itself a security boundary against kernel or VM escapes.
