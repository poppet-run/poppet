# Phase 37: Image and text-file attachments

[Implementation plan](../implementation-plan.md) · [Documentation index](../README.md)

Planned only. Let the owner attach images and small text files to a Discord
message or a CLI chat message, and pass them to the session's model. Phase 25
was removed because no adapter delivered attachments; this phase starts from
Discord intake and a provider that accepts images, and builds only what those
two need.

Do not add PDF extraction, voice transcription, outbound images, attachments in
scheduled task prompts, or images returned by MCP or browser tools. Do not
resize or re-encode images locally in this phase. Do not index attachment
contents for conversation search.

### Goal and compatibility gate

Today `IncomingMessage` carries only `text`, the Discord adapter drops a message
with empty content, and the shared provider `Message` has a text-only user role.
Both protocol encoders in `packages/provider/src/protocol` send user content as
a plain string. A screenshot or log file therefore has to be described or
pasted.

First verify each adapter's actual image input, and record the results in this
phase:

- ChatGPT: whether the account catalog response carries an input-modality field
  beside `slug` and `display_name`, and whether the Responses endpoint accepts
  an `input_image` part with a base64 data URL under `store: false`. Record the
  per-image and per-request size limits and the error for an unsupported model.
- OpenRouter: confirm `architecture.input_modalities` includes `image` for
  vision models, and that chat-completions `image_url` parts with data URLs are
  accepted through routing.
- OpenCode Go: test each model in `supportedModels` and mark image support only
  where a request with an image succeeds.
- Discord: record the attachment fields delivered with `MessageCreate`
  (`contentType`, `size`, `width`, `height`, `url`, `proxyURL`), how long CDN
  URLs remain valid, and whether the media proxy's `width`/`height` query returns
  a smaller image. That would let large phone photos fit the limits without local
  resizing.
- Worker: the size limit on CLI chat requests forwarded to the worker, since
  attachment bytes travel with the request.

Stop the image stages at this gate if no adapter accepts images. Text files can
still proceed alone because they become text parts.

### Stage 37a: Image input as a provider capability

Add `images: boolean` to `ModelDescription.capabilities`. Each adapter sets it
from verified metadata only: the OpenRouter modality list, the ChatGPT catalog
field if one exists, and a static flag per OpenCode model. Unknown means false.

Extend the user `Message` with optional ordered `parts`. Each part is a text part
or an image part with `mediaType` (`image/png`, `image/jpeg`, `image/webp`, or
`image/gif`) and base64 `data`. When `parts` is present, `text` remains the
owner's typed text. Responses encodes images as `input_image` content items, and
chat-completions encodes them as `image_url` parts. A request with an image for a
model without the capability fails before any network call with an
invalid-request error that names the model.

Extend the shared provider contract cases with an image request, a text-only
request whose encoding is unchanged, and the unsupported-model rejection.

### Stage 37b: Durable attachment storage

Add store migration 3 with an `attachments` table: id, session id, SHA-256,
media type, byte size, optional width and height, original filename, created
time, and a `BLOB` body, with `STRICT` and a foreign key to `sessions`. Keep the
bytes in the database rather than beside it so that backup, recovery, and
`0600` ownership from [storage](../storage.md) cover them unchanged. Saved user
messages reference attachments by id in their payload and never embed base64.

`assembleContext` resolves references to image parts only for the exchanges it
retains. `contextSize` counts each image at a fixed estimate instead of its
base64 length, so one screenshot cannot evict the whole history. Add
`chat.attachments` policy limits with conservative defaults: 4 files per
message, 5 MiB per image, 64 KiB per text file, and at most 8 images per request.
Images in older retained exchanges beyond the request cap become a text
placeholder naming the attachment id and filename. A missing or unreadable
attachment fails the run with the existing `history` reason rather than sending
a partial exchange.

Attachment contents are untrusted content. A run that includes an attachment
enters the same withdrawn-tool state as a fetched page, so task, memory, and MCP
mutations are proposed rather than performed. This matches the policy that
already lists attachments, and instructions say so.

### Stage 37c: Discord intake

Add `attachments` to `IncomingMessage` with filename, declared media type, size,
optional dimensions, and the CDN URL, at most 4 entries. A message with
attachments and no text is accepted. The bot mention rule and owner and scope
checks are unchanged. Text control commands ignore attachments.

Download during intake, before `repo.accept` commits the inbox entry, so that
retries and worker restarts never depend on an expiring CDN URL. Downloads:

- accept only `https` URLs on `cdn.discordapp.com` or `media.discordapp.net`,
  refuse redirects to other hosts, and apply a deadline and a streaming byte
  limit that does not trust the declared size;
- check the media type from magic bytes, and reject a mismatch with the
  declared type;
- request a smaller rendition through the media proxy when the gate shows it
  works and an image exceeds the limit.

Rejected or failed attachments get one reply that names the file and the
reason, and the message is not run. Partial acceptance would let the model
answer without input the owner thinks it has. Adding the
`ChannelError` reason `attachment` covers these replies.

A session whose model lacks image support replies with that before running and
suggests starting a new thread, since phase 34 owns model choice.

### Stage 37d: CLI attachments

Add a repeatable `--attach <path>` to `chat new` and `chat send`, placed before
the message like the existing options. The CLI reads and validates each file
with the same limits and magic-byte check, and resolves paths relative to the
working directory. When the worker serves the request, the CLI forwards bytes
within the size recorded at the gate and never forwards a path. Interactive chat
gains `/attach <path>`, which adds a file to the next message.

`chat show` and Discord `/status` list each message's attachments by id, type,
size, and filename. They never print the contents.

### Stage 37e: Text files

Accept UTF-8 files whose extension is on an allowlist (`.txt`, `.md`, `.log`,
`.csv`, `.json`, and common source extensions), within the text-file limit and
with no NUL bytes. The extension decides acceptance; Discord's declared type
does not. They are stored like images and become text parts headed by the
filename and attachment id, marked as untrusted file content. They count toward
the context budget at their real size and need no provider capability.

### Implementation reach and completion gates

| Area          | Required changes                                                                                  |
| ------------- | ------------------------------------------------------------------------------------------------- |
| Provider      | `images` capability, user `parts`, Responses and chat-completions encoding, contract cases        |
| Adapters      | Verified image metadata for ChatGPT, OpenRouter, and OpenCode Go                                  |
| Store         | Migration 3 `attachments` table, message references, reads scoped to the session                  |
| Agent         | Reference resolution, image size estimate, per-request cap, placeholders, untrusted-content state |
| Gateway       | `IncomingMessage.attachments`, empty-text acceptance, intake before commit, rejection replies     |
| Discord       | Attachment mapping, bounded CDN download, optional media-proxy rendition                          |
| CLI           | `--attach`, interactive `/attach`, worker forwarding, `chat show` listing                         |
| Config        | `chat.attachments` limits with startup validation                                                 |
| Documentation | Chat, CLI, Discord, configuration, storage, provider guides, architecture trust section           |

Test with injected HTTP and fake providers. Cover encoding for both protocols,
unsupported-model rejection before any request, limits per file, per message,
and per request, magic-byte mismatch, off-host and redirected URLs, truncated
downloads, empty-text messages with attachments, retries after the CDN URL is
gone, placeholder substitution in long sessions, and tool withdrawal after an
attachment. Run both migrations against temporary databases that contain
existing sessions.

Run focused tests and `bun run check`. Manually send a screenshot and a log file
in one Discord thread and with `chat send --attach` against each provider whose
gate passed, then confirm the answer describes their contents. Also send an
image to a text-only model and an oversized phone photo. Fake-provider tests do
not establish that a live model saw the image.
