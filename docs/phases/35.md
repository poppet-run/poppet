# Phase 35: Parallel messaging conversations

[Implementation plan](../implementation-plan.md) · [Documentation index](../README.md)

Implemented Stages 35a and 35b with automated checks; the default stays at one
concurrent request because the provider gate failed for `openai-chatgpt` (see
below). Let requests from different messaging conversations run at the same
time, so a long run in one Discord thread no longer delays a reply in another.
Requests within one conversation stay strictly ordered. Do not add per-conversation
models, priorities, or a scheduler for model work; the change is a bounded number
of concurrent runs.

### Implementation status

- Agent: `AgentLive` holds a permit per session, then one of
  `chat.maxConcurrentRequests` shared slots (1–8, default 1), for the whole
  `send` stream. Session permits are removed when unused. An interrupted waiter
  creates no run.
- Store: a third serialization point the plan missed. The baseline's
  `one_active_run` unique index and `queueRun` allowed one pending or running run
  across all sessions, so a second concurrent run failed with a conflict. Store
  migration 2 replaces it with `one_active_run_per_session`, and `queueRun`
  checks only its own session. This is the schema change the plan did not expect.
- Gateway: `repo.claim` moves an entry from `queued` to `executing` only once.
  `dispatchNext` claims entries while fewer than the agent's limit are running and
  runs each in a `FiberSet` owned by the gateway run; a finished request wakes the
  inbox. `RunningRequest` maps inbox IDs to `{ entry, fiber }`, and `/cancel`
  interrupts every running entry in its conversation. Claiming and `/cancel` share
  a lock so a cancel never misses a request being claimed. `processNext` keeps its
  claim-one-and-wait behavior, which tests use.
- Tests cover two sessions running at once with a third waiting for a slot, two
  sends to one session staying ordered without the waiter holding a slot,
  cancelled waiters creating no run, concurrent store transactions and gateway
  `attach` calls, refused duplicate claims, conversations outnumbering slots
  while each stays in order, `/cancel` interrupting only its thread, a CLI send
  waiting for a busy gateway session, two concurrent approvals with a reply in the
  wrong thread and `/cancel` in one of them, and shutdown with two active requests
  recovering on restart. Existing gateway and chat tests pass unchanged with the
  default limit of 1. `bun run check` passes.

Gate results:

- Store: Effect's Bun SQLite client leases its single connection through one
  semaphore for every query and whole transactions, so concurrent transactions
  never interleave. Passed, with the active-run index change above.
- Providers: failed for `openai-chatgpt`. The CLI resolver builds the provider
  layer inside each request's scope, and `CredentialStoreLive` takes the
  exclusive `auth/owner.lock` for that lifetime, so a second simultaneous
  ChatGPT request fails with `credential_store_busy`. `ChatGPTAuthLive`'s
  refresh semaphore is also per build, so it would not make concurrent refreshes
  happen once. API-key providers (OpenRouter, OpenCode) take no per-request lock.
  A 429 is not retried: `failureDecision` retries only channel failures, and a
  run is always saved before model resolution, so a provider rate limit fails
  the run with the standard failure reply. The default stays at 1 until the
  ChatGPT credential lock is shared within the worker process.
- Tools: browser resources are per run, Bash takes an absolute `cwd` per call,
  MCP servers have a lock each, task commands use `commandLock`, and the OpenAI
  model catalog cache is locked. No other shared mutable tool state was found.
- Memory: facts are keyed rows written in transactions; two runs saving different
  keys save two facts, and `remember` on an existing key is a conflict rather than
  an overwrite. Each run reads memory once when it starts.

Remaining work and manual checks: fix the ChatGPT credential lock, then raise the
default to 3. With an API-key provider and `chat.maxConcurrentRequests` set to 2
or more, run the worker, start a long request in one Discord thread, mention
Poppet in another channel while it is still working, and confirm that the second
reply arrives first. Then send a follow-up in the first thread before it finishes
and confirm the replies arrive in order. Record how often approvals wait in
practice. This does not show how a provider behaves near its rate limits.

### Goal and current behavior

Two separate locks make all model work serial today:

- `processNext` in `packages/gateway/src/execution.ts` forks one request and waits
  for it with `Fiber.await` before claiming the next. One `loop` drives it, and
  `RunningRequest` in `packages/gateway/src/context.ts` holds a single
  `current` entry.
- `AgentLive` in `packages/agent/src/service.ts` takes one permit from
  `Semaphore.make(1)` for the whole `send` stream, which serializes messaging,
  interactive chat, and scheduled runs together.

A command approval waits up to two minutes while it holds both. During that time
every other conversation, chat command, and scheduled occurrence waits too.

The inbox query `repo.next` in `packages/gateway/src/repository.ts` already orders
only within a conversation: an entry waits while an earlier entry with the same
parent and conversation (or external message ID for a fresh mention) is queued or
executing. A mention in a parent channel therefore never blocks a mention in
another channel. This phase keeps that rule and removes the serial waits around it.

### Compatibility gate

Confirm before changing behavior, and stop and record the gap if one fails:

- The SQLite client in `packages/store/src/database.ts` handles concurrent
  `withTransaction` calls from separate fibers without interleaving statements or
  returning `busy`. Write a store test that runs two `queueRun`/`startRun`/
  `finishRun` sequences and two gateway `attach` calls in parallel.
- Each provider adapter tolerates two simultaneous streams on one account. Check
  that OpenAI auth's token semaphore refreshes once and both requests use the new
  token. Check that a subscription concurrency limit or 429 maps to a retryable
  `ProviderError` that `failureDecision` retries before a run exists, and does not
  fail a run already in progress without an answer.
- Tools that hold state are per run or locked: browser sessions are created per
  run, Bash takes an absolute `cwd` on every call, MCP servers have a lock each,
  and task commands use `commandLock`. List any tool with shared mutable state
  that this survey missed.
- Memory writes from two runs at once land as two separate saved facts, and a run
  does not need facts written by a concurrent run. Each run reads memory once when
  it starts, so a concurrent fact appears in the next run. Document this; do not
  add cross-run memory notification.

### Stage 35a: Per-session and bounded agent permits

Replace the single request permit in `AgentLive` with two:

- A permit per session ID, held for the full `send` stream, so two sends to one
  session never read the same history and save out of order. This covers a CLI
  chat sent to a session that a gateway conversation is also using. Remove a
  session's permit when no one holds or waits for it.
- A global permit with `maxConcurrentRequests` slots, a new bounded `ChatSettings`
  value (1–8). Take the session permit first, then the global one, and release in
  reverse order, so a request waiting on a busy session does not hold a slot.

Keep the naming semaphore as it is. Keep cancellation before the run is created:
an interrupted waiter on either permit creates no run.

Default `maxConcurrentRequests` to 1 in this stage, so behavior is unchanged and
the per-session permit can be tested alone.

### Stage 35b: Concurrent gateway dispatch

Turn `processNext` into a dispatcher that claims entries while the concurrency
limit has room:

- Claim atomically. `repo.next` returns an entry still `queued` until `execute`
  marks it `executing` after `prepareSession`, so two fibers can claim the same
  entry. Add `repo.claim(id)` that sets `executing` only `WHERE state = 'queued'`
  and reports whether it changed. Call it right after `next`, before forking.
  Recovery already requeues `executing` entries with no saved run, so claiming
  earlier is still safe after a crash.
- Fork each request into a `FiberSet` (or a scoped `FiberMap` keyed by inbox ID)
  owned by the gateway run, so worker shutdown interrupts every active request and
  leaves them `executing` for recovery.
- Wake the inbox signal when a request finishes, so a waiting request in the same
  conversation starts without waiting for the five-second fallback.
- Use the agent's `maxConcurrentRequests` as the gateway limit too, so the gateway
  never claims more requests than the agent can start. Scheduled runs and CLI chat
  compete for the same agent slots; the gateway does not reserve any.

Once this is in place, set the default `maxConcurrentRequests` to 3, subject to the
gate's provider results.

### Running requests and `/cancel`

Replace `RunningRequest.current` with a map from inbox ID to `{ entry, fiber }`.
`execute` updates its own entry's `conversationId` and `sessionId` after
`prepareSession`, as it does now for `current`.

`/cancel` keeps its reply and scope: it cancels queued entries in its conversation
with `repo.cancel`, then interrupts every running entry whose `conversationId`
matches. Per-conversation ordering means there is at most one, but do not rely on
that in the lookup. A request in another conversation is never interrupted. A
mention that has not yet created its thread cannot be cancelled from a thread,
the same as today.

### Approvals

`commandApprovals` already keys pending decisions by a random ID and checks the
conversation when one is answered, so concurrent approvals in different threads
work without changes. Add tests for two pending approvals at once, a reply in the
wrong thread, and `/cancel` in one thread while the other waits.

A request waiting for approval keeps its agent slot for up to two minutes. Do not
release the slot during the wait in this phase. Record how often approvals wait
in practice, and only revisit if waiting approvals use up every slot.
