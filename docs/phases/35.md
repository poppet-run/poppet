# Phase 35: iOS app for chat and worker management

[Implementation plan](../implementation-plan.md) · [Documentation index](../README.md)

Planned only. Build a native iOS app that talks to a running worker: a chat
interface with one thread per session, plus screens for scheduled tasks, MCP
servers, memory, and worker status. Chat uses the existing
[web chat](../web-chat.md) HTTP API unchanged. Management needs new HTTP routes
because tasks, MCP, memory, and status are reachable only through the local
Unix socket today.

### Goal and compatibility gate

The web chat listener already provides login, the session list, conversation
snapshots, idempotent submissions, stop, and a server-sent event stream of full
snapshots. Replies run in worker-scoped fibers, so they continue while the app
is suspended or closed, and reopening a conversation reads its current
snapshot. The app adds no second execution path and holds no provider
credentials.

First verify that a non-browser client can use the listener as it stands. With
curl, log in using the access key, keep the session cookie, send non-GET
requests with an `Origin` header equal to `web.json`'s `origin`, submit a
message, and read the event stream. Stop at this gate if any step needs a
browser. In that case stage 35a must start with a server change, and that
change needs its own review of the Host, Origin, and cookie checks.

#### Gate result, 2026-11-15

The gate passes at the HTTP level. The check used curl against a worker with a
temporary data directory, its own access key, and no provider credentials, at
commit `df03612`.

| Request                                         | Result                                      |
| ----------------------------------------------- | ------------------------------------------- |
| Session list without a login                    | 401                                         |
| Login or submission without `Origin`            | 403                                         |
| Login with `Origin`                             | 200 and a session cookie                    |
| Session list with the cookie                    | 200                                         |
| Submission with an uppercase UUID               | 400                                         |
| Submission with a lowercase UUID and `Origin`   | 202, accepted receipt, new session          |
| Event stream                                    | Snapshots on change, a comment every 500 ms |
| Same submission ID and text again               | 202 with the saved receipt, no second run   |
| Same submission ID with different text          | 409                                         |
| Receipt, snapshot, stop, and logout             | 200                                         |
| Session list after logout                       | 401                                         |
| HTTPS origin, backend request with another Host | 403                                         |
| HTTPS origin, backend request as a proxy sends  | 200 and a `__Host-poppet` Secure cookie     |

The HTTPS rows sent plain HTTP to the loopback listener with the public `Host`
and `Origin`, as a reverse proxy does. That cookie then worked for the session
list and a follow-up submission to the existing session.

Still unverified:

- A completed reply. Without credentials the run failed, so the stream showed
  the receipt move from accepted to failed and carried no reply text.
- A real reverse proxy, including TLS and event-stream buffering.
- `URLSession` sending a custom `Origin` header. Confirm this in the first app
  build before building further on stage 35a.

The app lives in a separate repository. The Bun workspace's tooling and checks
do not fit an Xcode project, and this repository's changes are limited to the
worker's HTTP routes and documentation.

### Stage 35a: Chat against the existing API

Build the app with SwiftUI, Swift 6, and Observation. Use one dependency for
Markdown rendering, since code blocks and tables need more than
`AttributedString` provides. Remove inline images, as the browser does.

- Pairing asks for the HTTPS origin and the access key and saves both in the
  Keychain. Logins expire after 12 hours and end when the worker restarts, so a
  401 triggers one silent login before the request fails.
- A `NavigationSplitView` shows the session list as the sidebar and the
  transcript and composer as the detail, which also fits iPad.
- One client actor owns `URLSession`, Codable mirrors of
  `apps/web/src/api/protocol.ts`, and the event stream as an `AsyncSequence`.
  The stream reopens after an error and when the app returns to the foreground.
- The server remains the source of truth. The app keeps no local database.
- An unacknowledged submission is saved to disk until its receipt arrives, then
  recovered with the same ID. The app never resubmits automatically, matching
  the web recovery and forget behavior.

Submission IDs must be lowercase UUIDs; the server rejects the uppercase form
Swift produces by default. Every non-GET request must carry the configured
`Origin`.

This stage keeps web chat's limits: no attachments, search, renaming, model
selection, reasoning display, or command approval.

### Stage 35b: Management routes and screens

Add authenticated routes to the web listener for tasks, MCP inspection, memory,
and worker status. Each route decodes the existing command schema and calls the
same command function as the socket and local paths: `TaskCommand` handling in
`@poppet/tasks`, `inspectMCP`, `manageMemory`, and the worker status reader.
The general `/v1/commands` endpoint stays off the network. Routes reject unknown
fields and reuse the listener's login, Host, and Origin checks.

The app adds a Tasks tab and a Settings tab:

- Tasks: list, detail with recent occurrences, add, edit, delete, pause,
  resume, skip, snooze, and run-now.
- MCP: servers, connection status, and each server's allowed tool catalog.
  This is read-only. Adding, enabling, or disabling a server still means
  editing `config.json` and restarting the worker.
- Memory: list, set, replace, and forget facts.
- Status: worker services, messaging state, provider pauses, and recent
  outcomes.

A task created in the app has no Discord or Slack conversation to inherit, so
its results appear only in task history unless the owner selects an explicit
destination. Decide during this stage whether the add form offers the home
channel as a destination.

### Stage 35c: Chat parity

Expose session rename and conversation search over HTTP using the existing
store operations, then add them to the app. Add attachments by routing uploads
through the agent's existing validation and storage path, within the limits the
gateway already applies. Model selection at session creation depends on
[phase 34](34.md) and uses its aliases; without that phase the app keeps using
the configured provider and model.

### Stage 35d: Notifications and approvals

Send Apple push notifications from the worker using the owner's own signing
key, stored with protected channel credentials and excluded from logs and
ordinary configuration. Register the app as a task delivery destination through
the gateway's durable reply queue, so notification failures never rerun
inference. Supply an approval callback for app-started runs so the owner can
approve or deny a reviewed Bash command, scoped to the originating session and
held for the existing two-minute limit.

This stage needs a paid Apple developer account and outbound connections from
the worker to Apple. Without it, approvals work only while the app is open.
Treat this stage as optional; stages 35a–35c do not depend on it.

### Implementation reach and completion gates

| Area          | Required changes                                                                         |
| ------------- | ---------------------------------------------------------------------------------------- |
| CLI web chat  | 35b management routes, 35c rename, search, and upload routes, 35d approval callback      |
| Web protocol  | Shared types for the new routes, kept in `apps/web/src/api/protocol.ts`                  |
| Tasks, MCP    | No behavior changes; existing command schemas and functions are reused                   |
| Gateway       | 35d only: an app delivery destination and notification sender                            |
| iOS app       | Separate repository: client, pairing, chat, management screens, notifications            |
| Documentation | Web chat guide for the new routes, a new app guide, worker and architecture web sections |

Test each new route in the existing web chat suite with the controlled test
provider and a temporary data directory: unauthenticated requests, a wrong
`Origin`, unknown fields, and parity with the socket command for the same
input. Confirm the listener still does not expose the general command endpoint.
Run focused tests and `bun run check`.

In the app, test the client against recorded responses: snapshot decoding,
event stream reconnection, login renewal after a 401, and submission recovery
with one saved input. Keep interface tests to the pairing and send paths.

Manual checks on a device, against a real worker over HTTPS:

1. Pair, send a message, and compare the reply with the browser.
2. Background the app during a reply, reopen it, and confirm the reply
   completed once.
3. Drop the network during submission, reconnect, and recover it. Confirm one
   input in `poppet chat show`.
4. Restart the worker and confirm the app logs in again without asking for the
   key.
5. Create, pause, and run a task from the app, and compare with
   `poppet tasks show`.

Fake-provider tests do not establish that a live provider or Apple's
notification service behaved as expected.
